## 1. 访问仓库

- 远端是**公开仓库** `https://github.com/dlg591103-cpu/webgis-twin-lab`，可直接克隆，无需邀请。
- 有 Write 权限的协作者（`PINGNINGYI`）可直接在仓库内推送任务分支；其他贡献者先 Fork，再向上游发起 Pull Request。
- `main` 受分支保护，任何人都不能直接推送，包括维护者；变更一律经 PR 评审后合并。
- 接受邀请后，可创建 `docs/test-collab` 分支做一次文档小改动并推送，确认 Write 权限已生效。

## 2. 克隆

```powershell
git clone https://github.com/dlg591103-cpu/webgis-twin-lab.git
cd webgis-twin-lab
git log --oneline -3
```

没有 Write 权限时改用 Fork 地址，并添加上游：

```powershell
git remote add upstream https://github.com/dlg591103-cpu/webgis-twin-lab.git
git fetch upstream
```

克隆目录名与本地开发目录名不必一致，项目内部无硬编码路径依赖；若发现硬编码，按缺陷处理。

## 4. 认领任务与建分支

- 分支怎么建、基线怎么定：见 [工程规则.md](工程规则.md) 第 1 节。基线是 `main` 上一个**固定提交**，开工时记下 `git rev-parse upstream/main`（无写权限）或 `git rev-parse main`（有写权限）的结果。
- 谁做哪部分、各窗口独占哪些文件：见 [SPEC 6.1 并行分工与文件归属](Spec/V0.1-专题制图智能体.md)。表内的独占文件归属优先于"顺手改一下"的冲动。
- 分支名沿用 SPEC 表内的 `feat/core`、`feat/data-steward`、`feat/cartographer`、`feat/reviewer`；新增窗口另行取名并在 SPEC 6.1 登记。
- **不要直接改 `main`。** 需要改共享文件（`spec.py`、`loop.py`、`app.py`）时，按 SPEC 6.1 的协作规则处理。

## 6. 交付要求

- 交付一份**明确提交**（给出提交 SHA）和自检结果，不要把"本地跑通了"当作交付。
- 自检记录与独立验收记录分别保留，具体格式与归属见 [工程规则.md](工程规则.md) 第 3、4 节。
- 只改自己名下的文件；确实需要动无关功能时，单独说明原因与范围（第 8 节）。
- 不得声称未实际完成的操作，未验证的范围要写明"未验证"（第 6 节）。

## 7. 明确不要做的事

- 不直接向 `main` 推送、不自行合并回 `main`——合并须经用户授权（[工程规则.md](工程规则.md) 第 4、6 节）。
- 不自行创建远端仓库、不代用户修改远端设置。
- 不把真实用户数据、密钥、大体积原始数据提交进仓库（见 `.gitignore` 与事实文档 06 数据源）。
- 不改写 `docs/facts/` 里已确认的内容；发现不一致时提出冲突，等确认。
- 不冒用维护者身份提交。
- 不推上线：合并完成不等于已上线，上线须用户明确确认（第 6 节）。
